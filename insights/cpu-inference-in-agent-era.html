Agent 时代，为什么 CPU 推理优化反而更重要了？

当推理成为 AI 的主战场、当一次用户请求被放大成数十甚至上百次模型调用， "用 GPU 跑大模型" 不再是唯一答案。CPU 正在以 无处不在、海量内存、低成本闲置 的特性，重新回到 AI 推理栈的中心。

关键词：Agent · LLM 推理 · CPU 优化 面向：AI Infra / 系统研究 / 算法工程 视角：成本 · 延迟 · 隐私 · 能效

TL;DR — 一句话洞察

Agent 把"一次大模型推理"变成了 "一条由数十个长上下文、小批量、低延迟、异构模型组成的调用链"， 而这条调用链的瓶颈恰好落在 访存带宽、内存容量、调度灵活性、闲置弹性 —— 这正是 CPU 相对 GPU 最有可能扳回的战场。

1趋势变化：从"训练为王"到"推理决定单位经济"

过去三年关注点是"如何把模型训得更大";Agent 时代关注点是"如何把模型用得更便宜、更快、更可控"。 这是一次工作负载性质的根本变化，下面六个事实直接推动了 CPU 重新被严肃对待。

①

调用次数被放大 10–100 倍

一次用户请求 = Plan + Tool Select + Reflect + Critique + Rerank + Guardrail + … 单步小、链路长，整体由"延迟和成本"主导，而不是单步峰值算力。

②

解码阶段是访存瓶颈

自回归解码本质是 权重 + KV cache 的内存搬运， 当 batch 很小（Agent 常态）时，GPU 算力大量闲置，差距收敛到访存带宽 + 内存容量。

③

GPU 在 Agent 链路中常被"卡住"

Agent 频繁等待工具调用、网络 I/O、人类输入。GPU 闲置 = 烧钱; CPU 天然适合"波动大、长尾、突发"的弹性负载。

④

小模型成为主力

路由、改写、嵌入、重排、判别、JSON 校验、函数调用…… 80% 的 Agent 内部调用其实是 1B–8B 量化模型，CPU 完全 hold 得住。

⑤

端侧 / 私有化 Agent 爆发

PC、手机、车机、IoT、企业内网。隐私、离线、个性化记忆 —— 这些场景里 GPU 不一定有，但 CPU 一定在。

⑥

现代 CPU 不再是过去的 CPU

Intel AMX、AVX-512 VNNI、ARM SVE2 / SME、Apple AMX、 CXL 大内存池，以及 INT4/INT8 量化在 CPU 上的成熟，让差距大幅缩小。

2对比视角：Agent 工作负载下 GPU 与 CPU 的真实差距

与"训练巨型模型"不同，Agent 的内部调用呈现出一组非常特殊的特征。把这些特征逐一展开， 就能看到为什么 CPU 不再是"备胎"，而是"互补主力"。

负载特征 GPU 倾向 CPU 倾向 Agent 实际场景
Batch size 大 batch 强 小 batch 不亏 每个 Agent step 通常 batch=1~4
上下文长度 受限于显存 DRAM 廉价 TB 级 记忆 + 历史 + 工具描述，动辄 100K+ token
调用形态 长稳态吞吐 突发 + 长尾 等工具、等用户、等检索 → 大量空闲
模型规模 70B+ 旗舰 1B–13B 量化 Router / Drafter / Embedder / Guard 多为小模型
部署位置 云端集中 端 / 边 / 云全覆盖 个人 Agent、企业内 Agent、隐私 Agent
每 token 成本结构 高资本开销 已有存量算力 Agent 长链路对 $/token 极度敏感
机密计算 生态尚浅 TDX / SEV / SGX 成熟 处理私有数据、企业知识、用户记忆

关键判断： 在 Agent 时代，"GPU 跑主力模型 + CPU 跑长尾 / 小模型 / KV / 调度 / 安全" 将是大多数生产系统的稳态形态。CPU 推理优化不是去取代 GPU， 而是去 填满 GPU 不擅长的所有缝隙，从而把整条 Agent 链路的端到端延迟和单位经济压下来。

3系统视角：Agent 推理栈中 CPU 的"真正位置"

把一个真实的 Agent 系统拆开看，CPU 远不只是"跑小模型"。它同时承担调度、KV、加密、 约束解码、工具桥接等关键角色。下面是一个典型的分层视图。

模型服务

推理内核

⚠

容易被忽视的事实： 即使一个 Agent 系统"主模型在 GPU 上"，它在 CPU 上仍然有 tokenizer、采样、约束解码、KV 管理、prefix 缓存、工具序列化、向量检索、安全审查 等大量关键路径。这些环节的延迟往往直接决定用户感知的"Agent 卡不卡"。

4关键研究方向：值得长期投入的 10 个方向

下面给出在 Agent 时代具有较高研究密度与工程价值的 CPU 推理方向。每一条都同时包含 "为什么重要" 与 "代表性技术 / 工作"，便于直接展开为研究计划或预研课题。

① CPU 友好的极致量化（W4A8 / W4A16 / FP8 / 混合精度）

Agent 链路对每 token 成本极敏感，量化是把模型放进 CPU 内存带宽预算内的前提。 重点在于：保 Agent 任务（推理、函数调用、JSON 输出）准确率，而不仅是 perplexity。

GPTQAWQSmoothQuant OmniQuantQuaRot / SpinQuant Activation-awareVNNI / AMX 适配

② CPU 专用算子与编译栈

充分释放 AMX / AVX-512 / SVE2 / SME 的算力，并解决 NUMA、cache locality、 prefetch 等访存问题。编译栈决定了"同一模型在 CPU 上能跑多快"的上限。

llama.cpp / ggmlOpenVINO GenAI oneDNNIPEX-LLM Triton-CPUMLIR / IREE TVM / MLC-LLM

③ 稀疏化与上下文相关稀疏（Contextual Sparsity）

FFN 与 head 的激活在解码阶段大量为零或近零，CPU 上跳过它们的收益比 GPU 更大 (CPU 控制流便宜)。MoE 在 CPU 上的稀疏路由也属于此方向。

Deja VuPowerInfer / PowerInfer-2 LLM-MQMoE-Lightning Activation SparsityHot/Cold neuron 划分

④ KV Cache 管理：压缩、复用、跨步缓存

Agent 多步对话 / ReAct 循环 / Multi-agent 之间存在大量 prefix 重叠， CPU 大内存 + 智能 KV 调度可以把"重复 prefill"几乎消掉。这是端到端延迟最大的优化空间之一。

PagedAttention / vLLMRadixAttention / SGLang H2OStreamingLLM KV 量化（KIVI / KVQuant）Prefix sharing

⑤ 推测解码与小-大模型协同（CPU 做 Drafter）

让 CPU 跑 Draft 模型、GPU 做 Verify;或在纯 CPU 场景中用 Medusa / EAGLE 把解码并行度拉起来。这是 CPU 在 latency 上"反超"的关键武器。

⑥ CPU↔GPU 异构调度与 Offloading

把热权重放 GPU、冷权重放 CPU/CXL，把短上下文放 GPU、长上下文放 CPU 内存， 把 Drafter / Embedder / Guard 放 CPU、把 Verifier 放 GPU。 Agent 工作负载的高度异构性使这条路线天然可行。

FlexGenFastDecode NEO / Hetero-servingCXL 内存池 动态权重迁移NUMA-aware placement

⑦ Agent 感知的推理系统（Agent-Aware Serving）

让推理系统理解"这是一个 Agent 调用链"，从而做： 前缀共享、跨步 KV 复用、工具调用期间 KV 暂存、语义级缓存、 优先级抢占、链路级 SLA 调度。这是一个目前明显缺位的研究方向。

SGLang语义缓存 / GPTCache 跨 step KV 复用Tool-aware scheduling 链路级 SLO

⑧ 约束解码 / 函数调用 / 结构化输出在 CPU 上的加速

Agent 极度依赖 JSON / Schema / 工具签名，约束解码本质是 每步采样都要乘上一个掩码。这个掩码计算在 CPU 上完全可以做到零开销， 但常被实现成主路径瓶颈。是被严重低估的工程方向。

⑨ 端侧 / 边缘 Agent 的全栈优化

个人 Agent、设备 Agent、车载 Agent 的核心约束就是"没有 GPU、有大量 DRAM、 必须低功耗"。CPU + NPU 协同、模型蒸馏、人格化记忆与隐私保护是一整套子领域。

⑩ 机密推理与可信 Agent（Confidential Inference）

Agent 处理大量私人 / 企业敏感数据。CPU 上的 TEE 生态明显领先 GPU。 如何在 TDX / SEV-SNP 中以可控开销跑量化 LLM 与 KV 缓存，是企业级 Agent 落地的硬门槛。

5给研究者 / 工程团队的实操建议

不是所有方向都同样"好下手"。以下是按"投入产出比 × 与 Agent 主流演进契合度"给出的优先级建议。

★

优先做：KV 复用 + 前缀共享

对 Agent 链路是 10× 量级的端到端收益，且 CPU 的大内存是天然优势，工程难度可控。

★

优先做：CPU Drafter 推测解码

在不牺牲精度的前提下提升解码并行度，特别适合 1B–8B 小模型直接在 CPU 上跑出 2–3× 加速。

★

优先做：约束解码内核优化

工程量小、收益直接、用户感知强；很多 Agent 卡顿其实来自 JSON 约束解码而非模型本身。

◇

中期投入：异构调度框架

需要同时改运行时、调度器、KV 系统，门槛高，但一旦做成是平台级护城河。

◇

中期投入：Agent-Aware Serving

当前服务系统把 Agent 视作"独立请求流"，留下大量未捕获的复用与共享机会。

○

长期下注：CPU 上的机密 Agent

面向企业市场与监管场景，护城河深、变现路径清晰，但需要硬件 + 内核 + 模型的全栈协同。

6结语：CPU 推理优化，是一场"被 Agent 重启"的老课题

十年前我们优化 CPU 推理，是因为没有别的选择;今天我们重新优化 CPU 推理， 是因为 Agent 把推理工作负载切成了无数小、长、散、敏感的碎片 —— 而碎片化负载的最优载体，从来不是峰值算力，而是无处不在、足够便宜、足够灵活的算力。

✦

一句记忆点： Agent 时代不是"GPU vs CPU"，而是"谁能让一条 Agent 调用链整体跑得更便宜更快"。 在这个新指标下，CPU 推理优化从"边缘话题"重新回到了 AI 系统研究的中央舞台。
