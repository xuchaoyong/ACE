面向网络配置意图的
命令行高准确率召回方案

以"命令树 + 真实配置"统计建模为骨架，离线用 LLM 读手册挖掘补漏规则， 在线先用静态知识库做第一步识别，再让 LLM 判定 + 查漏补缺。 三套知识源互相校验，把"漏召回"和"误召回"双向压下去。

输入 50K 命令 Recall ≥ 95% Precision ≥ 90% 可解释 / 可回放 参考 INTA / NAssim

01设计目标与核心思想

给定一个自然语言的用户意图，从设备全量的 50K 行命令中， 精准召回出实现该意图所需的**全部**命令，并按"进入视图 / 前置 / 主体 / 显示 / 撤销"分组排序。

骨架：统计

静态依赖知识库 G_stat

从命令树 + 真实历史配置中，用 Lift、PMI、PrefixSpan、对象引用解析等统计方法离线构建依赖图。

补漏：LLM 读手册

规则知识库 R_llm

按章节让 LLM 读 NAssim 结构化手册条目，产出 prerequisite / companion / exclude / scenario_template 四类规则。

在线：LLM 判定

LLM 精排 + 完整性复查

在线先由静态 KB 做第一步识别，再让 LLM 精排去伪、规则触发补漏，最后做一次反向 challenge 复查。

★

核心原则：宁多召回，少漏召回；让 LLM 当裁判而不是搜索引擎。

统计 KB 在毫秒级把候选从 50K 收敛到几百，LLM 仅看候选 + 手册原文做高精度判断；本地依赖图与 LLM 规则双兜底，避免漏前置 / 漏对象引用 / 漏 undo / 漏 display 这类典型缺失。

03阶段1：基于命令树 + 真实配置的静态依赖知识库

完全本地、可复现、可解释。统计阶段产物用作"高 Recall 兜底"。

3.1 输入与预处理

  • 命令行树：由 NAssim 风格抽取器产出，每条命令含 PageTitle / ParentView / FuncDef / ParaDef / Examples / ExtraInfo / feature / sub_feature。
  • 真实配置文件：N 份历史设备 config，越多越好，建议数千份起步。
  • 归一化：去时间戳/注释；接口名 → <IF>；ACL/模板/实例编号 → 占位符并保留 side-table。
  • 解析为配置实例树：按缩进 / view 嵌套，每个节点 = (命令模板, 参数值)；匹配回命令树取得命令 ID（最长前缀 + 视图约束）。
  • 未匹配落 log：作为命令树修订输入。

3.2 五类统计信号

N = 配置文件总数，f(A) = 出现 A 的配置数，f(A,B) = A、B 同现配置数。

① 共现强度（无序）

Lift(A,B) = (f(A,B)/N) ÷ ((f(A)/N) · (f(B)/N))

Conf(A → B) = f(A,B) / f(A)

PMI(A,B) = log( f(A,B)·N / (f(A)·f(B)) )

筛选示例：f(A)≥30 ∧ f(A,B)≥10 ∧ Lift≥3 ∧ Conf≥0.6 → companion 边。

② 顺序依赖（A 总在 B 之前）

PrefixSpan 频繁序列对挖掘 + 顺序比：

OrderRatio(A→B) = #{A 早于 B} / #{A,B 同现}

≥ 0.95 → precedes 边。

③ 视图链（结构性事实）

ParentView 给出视图嵌套；配置缩进做交叉验证。

任意 view 内命令 ⇒ 必有相应 view 入口命令。这是最强约束。

④ 对象引用图

解析参数值得 create / refer 关系：

acl number 2000 → CREATE acl:2000

traffic-filter ... acl 2000 → REFER acl:2000

建 object_ref 边，比共现可靠得多。

⑤ 特征 / 章节同族

命令树按 feature / sub_feature 自然分组，作为低权重 sibling 边。

长尾命令在统计样本不足时的兜底。

⑥ 派生：命令热度 + 命令簇

热度 = f(A)/N；社区发现（Louvain/Leiden）得"配置模块"，取代表命令作 anchor。

3.3 落库：依赖图 G_stat

边类型推导方式强度默认权重元数据
enter_view视图结构 + 缩进强约束1.0view chain

⚠

统计 KB 已知缺陷与缓解

· 罕见命令样本不足 → 用 sibling 兜底 + 阶段 2 LLM 规则补；
· 老化 config 含过时命令 → 按日期加权；
· 错误配置固化 → 设置最小 support 阈值，规则采样审计；
· 视图链解析失败 → 入 unmatched.log，反哺修订命令树。

3.4 单独看的预期效果

Recall 高（> 90%）、Precision 中（含同特性命令噪音），交给后续 LLM 收敛。

04阶段2：LLM 读手册产规则（补长尾）

对应 INTA 论文的"读手册"思想，但产物是机器可执行的规则而非配置。

4.1 LLM 输入单位：章节

  • 按 feature 章节喂入，包含若干 NAssim 命令条目；
  • 同时把 G_stat 在该章节内已挖出的依赖子图塞给 LLM；
  • LLM 做"合并 + 修正 + 长尾补全"，而不是从零编造。

4.2 规则四种类型

prerequisite 前置必加

某命令命中时必须补入的前置命令（进入视图、创建对象等）。

companion 搭配建议

常搭配命令，弱触发，受 effective_confidence 控制。

exclude 互斥剔除

意图含某关键词且候选含某命令时显式删除，解决易混淆（802.1p vs 802.1x）。

scenario_template 场景模板

整套有序命令模板，主力提升完整性。

4.3 规则输出 schema

{
  "feature": "Class-based QoS / DiffServ Domain",
  "rules": [
    {
      "id": "DSDOMAIN-001",
      "type": "prerequisite",
      "if": {"candidate_includes": ["8021p-inbound"]},
      "then_add": ["diffserv domain", "system-view"],
      "evidence": "8021p-inbound 的 ParentView 是 DiffServ domain view",
      "confidence": 0.95,
      "source": "manual_chapter_QoS"
    },
    {
      "id": "DSDOMAIN-003",
      "type": "exclude",
      "if": {"intent_keywords": ["802.1x"], "candidate_includes": ["8021p-inbound"]},
      "then_remove": ["8021p-inbound"],
      "evidence": "802.1p 是 QoS 而非认证, FuncDef 明确",
      "confidence": 0.99
    },
    {
      "id": "SCENARIO-DS-INBOUND-8021P",
      "type": "scenario_template",
      "if": {"intent_scenarios": ["DS 域入方向 802.1p 映射"]},
      "then_include_ordered": [
        "system-view", "diffserv domain", "8021p-inbound"
      ],
      "evidence": "ExtraInfo · Usage Scenario 段",
      "confidence": 0.9
    }
  ]
}

4.4 规则与 G_stat 的对账（关键）

↔

LLM 产物不会直接生效，先对账：

① 统计支持：G_stat 存在同向边 ⇒ confidence ↑，标 cross_validated；
② 统计反对：Lift < 0.5（独立性强）⇒ confidence ↓，标 weakly_supported；
③ 冲突合并：多条规则触发条件重叠 ⇒ 按 confidence 排序，冲突的进入人工复核队列。

4.5 LLM 规则挖掘 Prompt（精简）

你是网络命令规则提炼器。下面是同一 feature 的若干命令手册条目，
以及统计学已知依赖。请输出 JSON 规则（schema 见示例），
仅输出能被手册 FuncDef/ParaDef/Examples/ExtraInfo 中至少一段文本直接支持的规则。

[手册条目 1..N]
[已知统计依赖：见表]

要求:
- 不要发明命令名 (only from manual entries provided)
- 每条规则必须有 evidence 字段引用对应手册片段
- 区分强约束 (prerequisite) vs 倾向 (companion)
- 若发现易混淆命令，输出 exclude 规则

05阶段3：在线召回流程

5.1 Step 1 · LLM 意图解析 → IntentSpec

把自然语言意图翻译成结构化 IntentSpec，所有后续步骤基于它。模糊意图允许多 IntentSpec 求并集。

{
  "summary": "在 DS 域内把 802.1p=2 的 VLAN 报文映射为 AF1 并标记为绿色",
  "features": ["QoS", "DiffServ"],
  "sub_features": ["Class-based QoS", "DS Domain"],
  "action_types": ["configure", "display"],
  "objects": [
    {"name": "DiffServ domain", "instance": "test"},
    {"name": "802.1p", "value": 2},
    {"name": "PHB", "value": "AF1"},
    {"name": "color", "value": "green"}
  ],
  "direction": "inbound",
  "must_have_keywords": ["DiffServ", "802.1p", "AF1", "color"],
  "out_of_scope": ["IPv6", "BGP", "802.1x"]
}

5.2 Step 2 · 静态 KB 第一步识别（完全本地，毫秒级）

  1. 种子识别：依据 objects/features 找 anchor 簇 + must_have_keywords 命中 PageTitle/FuncDef → S_seed（10~30 条）。
  2. BFS 图扩展（深度 ≤ 3，加权）：
    • enter_view 边：祖先视图入口必扩展；
    • object_ref 边：引用两端必扩展；
    • precedes 边：前置命令必扩展；
    • companion 边：按 lift 取 top-K；
    • sibling 边：仅在同 feature 时小幅扩展。
  3. 输出候选 S_0（200~500），每条携带"经过哪条边 / 哪些统计指标"作为证据。

5.3 Step 3 · LLM 判断 + 规则触发（去伪 + 补漏）

3.1 LLM 精排

按 batch 喂 IntentSpec + 每条命令 NAssim 摘要，输出 {relevance:0~3, role, must_include, reason}。relevance ≥ 2 保留。

3.2 规则触发

跑 R_llm 规则引擎：prerequisite/companion/exclude/scenario_template 触发，所有新增必须在知识库已知命令中。

3.3 完整性复查

把 S_1 整体回给 LLM 做反向 challenge：缺 enter_view？缺对象创建？缺 undo？所有建议二次校验。

5.4 Step 4 · 结构化分组输出

按 role 分组：enter_view prerequisite primary companion display undo，并按视图链排成可执行顺序，每条命令附证据链与置信度。

06准确率保障机制

准确率风险责任承担者
漏前置 / 对象引用命令G_stat 的 enter_view + object_ref 边（结构性） + R_llm 的 prerequisite 规则双兜底
漏冷门搭档G_stat companion + R_llm companion 规则双源补全
漏 undo / displayR_llm 的 scenario_template + LLM 完整性复查
易混淆命令误召（802.1p vs 802.1x）R_llm 的 exclude 规则 + LLM 精排显式判断
LLM 幻觉新增不存在的命令所有增删强约束"必须来自知识库已知命令"，否则丢弃
规则 ↔ 统计冲突对账阶段做置信度合成，未解冲突进人工队列
✓

可解释链路：每条召回都能回答三问 — "统计上凭什么相关 / 哪条规则触发了 / LLM 给的相关性多少分"。

④ Step 3.2 · 规则触发（R_llm）

prerequisite 命中：DSDOMAIN-001

if: candidate 含 8021p-inbound ⇒ then_add: diffserv domain, system-view。两条已经在 S_0 中，标 rule_confirmed。

exclude 命中：DSDOMAIN-003

if: intent_keywords 含 802.1x 且 candidate 含 8021p-inbound。本意图未含 802.1x，但 out_of_scope 含之，触发"反向 exclude"：从 S_0 移除疑似混淆项 8021x port-method。

scenario_template 命中：SCENARIO-DS-INBOUND-8021P

intent_scenarios 命中 "DS 域入方向 802.1p 映射"。模板 then_include_ordered: system-view → diffserv domain → 8021p-inbound，已全部存在，不新增。

companion 命中：DSDOMAIN-DISPLAY-001

intent action_types 含 display，且 candidate 含 diffserv domain。建议补 display diffserv domain application（已在知识库），加入候选。
